# NCombat Security Analysis

Generated by Charles using Claude Code under Opus 4.7 (high effort).

**Date:** 2026-05-23
**Branch:** security
**Scope:** Source tree under `/home/pcuser/Projects/ncombat` — primarily the active Spring Boot module (`pom.xml`, `src/main/**`). The legacy `bin/` WAR module is called out separately.

This is a defensive code review intended for the project maintainers. Findings are ranked by severity. Each finding includes a description, evidence (`file:line`), impact, exploitation sketch, and remediation. A short executive summary appears at the top.

---

## Executive Summary

NCombat is a multiplayer text-based combat game implemented as a Spring Boot 2.2.6 web application with a jQuery 1.3.2 frontend. The application has **no security framework configured** (no Spring Security, no CSRF tokens, no authentication on admin endpoints, no transport security), and runs on top of **substantially out-of-date dependencies with known critical CVEs**. The frontend uses `eval()` on Ajax responses, and player-supplied text is rendered into the DOM without explicit HTML escaping on the client side (a defense-in-depth concern, not an immediately exploitable XSS in modern browsers).

The single most urgent items are:

1. **Upgrade Spring Boot** off the EOL 2.2.x line (Spring4Shell and many other CVEs apply).
2. **Replace jQuery 1.3.2** (multiple known XSS CVEs) — or, better, remove `eval()` and the jQuery dependency entirely.
3. **Add authentication** to the admin endpoints.
4. **Add CSRF protection and session fixation prevention** by introducing Spring Security.

Because the application is internet-exposed as an anonymous game, some "missing auth" issues are by design — but admin endpoints, session handling, and transport security are not.

### 1. EOL Spring Boot 2.2.6.RELEASE — Critical

**Evidence:** `pom.xml:11` declares `<version>2.2.6.RELEASE</version>` of `spring-boot-starter-parent`.

**Impact:** Spring Boot 2.2.x reached end-of-life in 2020. The 2.2.6 release (April 2020) predates many published CVEs in Spring Framework, Spring Boot, embedded Tomcat, Jackson, Log4j-bridge, SnakeYAML, etc. Notable examples that apply (directly or via transitive dependencies):

- **CVE-2022-22965 ("Spring4Shell")** — RCE via data binding on JDK 9+ when running on Tomcat as a WAR. The active build is an embedded-JAR Spring Boot run, which mitigates the original PoC but does not eliminate exposure for any downstream packaging.
- **CVE-2022-22950** — Spring Expression DoS.
- **CVE-2023-20861 / CVE-2023-20860 / CVE-2023-20863** — Spring Framework SpEL/path-pattern vulnerabilities.
- Numerous embedded-Tomcat CVEs from 2020–2024 (request smuggling, response header injection, etc.).
- Jackson `2.10.x` databind CVEs (polymorphic deserialization) if any Jackson typing is enabled.

**Remediation:** Upgrade to a supported Spring Boot 3.x line (or at minimum 2.7.18 with commercial support). This is the highest-leverage fix and resolves a long tail of transitive CVEs in one move. Track via `./mvnw dependency:tree` + OWASP Dependency-Check (`org.owasp:dependency-check-maven`).

### 2. jQuery 1.3.2 — High

**Evidence:**
- `src/main/resources/static/html/lib/jquery-1.3.2.js` (committed copy)
- `src/main/resources/templates/ncombat.html:7`, `templates/ncombat2.html:7`, `templates/admin.html:7` load it.

**Impact:** jQuery 1.3.2 was released in 2009. Affected by at least:

- **CVE-2012-6708** — selector-based XSS via `$()` accepting HTML.
- **CVE-2015-9251** — XSS via cross-domain Ajax + `text/javascript` content-type.
- **CVE-2019-11358** — prototype pollution in `$.extend(true, …)`.
- **CVE-2020-11022 / CVE-2020-11023** — XSS through `.html()`, `.append()`, etc., when handling untrusted HTML.

Several of these are directly reachable: the templates call `$('#prompt').html(data.prompt)` (CVE-2020-11022/23 surface).

**Remediation:** Upgrade to jQuery 3.7.x at minimum, or — preferred — remove jQuery entirely. The amount of jQuery actually used (`$.ajax`, `$().html`, `$().css`, `$().load`, `$.getJSON`) is small and trivially replaceable with `fetch` and `Element.textContent`.

### 3. `eval()` of Server Response — High

**Evidence:**
- `src/main/resources/templates/ncombat.html:21` — `eval('var data = ' + xhr.responseText + '.data');`
- `src/main/resources/templates/ncombat2.html:21` — same pattern.
- `src/main/resources/templates/admin.html:19` — same pattern.

**Impact:** `eval()` parses the entire response as JavaScript. Today this is mitigated by:
1. Jackson serializing JSON with proper escaping.
2. Same-origin policy preventing cross-origin response injection.

But the pattern is fragile and bites in several scenarios:

- **Network-level MITM** (the app is HTTP-only — see finding #7) — a network attacker can rewrite the response body to inject arbitrary JS, which then runs in the user's browser with full access to cookies and the page DOM. This is the realistic exploit.
- Any future endpoint that returns a value Jackson does not escape correctly (custom serializer, raw `@ResponseBody String`, error pages, etc.) becomes a direct code-execution sink.
- Defeats CSP attempts (would require `unsafe-eval`).

**Remediation:** Replace with `JSON.parse(xhr.responseText).data`, or — when Jacking jQuery — use `$.ajax({dataType: 'json'})` / `fetch().then(r => r.json())`, which never eval. Adding a strict `Content-Security-Policy` (no `unsafe-eval`, no `unsafe-inline`) will prevent regressions.

### 4. Unauthenticated Admin Endpoints — High

**Evidence:**
- `src/main/java/org/ncombat/web/AdminController.java:17,29` — `@RequestMapping("/admin.do")` + `@GetMapping` with no auth.
- `src/main/java/org/ncombat/web/AdminRestController.java:12` — `@GetMapping("/adminTest.json")` with no auth.
- Confirmed: a project-wide grep for `SecurityConfig`, `HttpSecurity`, `WebSecurity`, `@PreAuthorize`, `@Secured` returns **no matches**. There is no security filter chain.

**Impact:** Anyone who can reach the host on port 5000 can:

1. Hit `/admin.do` and read the game's start time and uptime (information disclosure today).
2. Hit `/adminTest.json` and confirm the admin REST surface is reachable.

The admin page is currently read-only, so impact today is limited to information disclosure and reconnaissance. However, the endpoint name and structure strongly suggest more privileged operations are expected to be added — landing them on this unprotected path is dangerous.

**Remediation:** Add `spring-boot-starter-security`, configure a `SecurityFilterChain` that requires authentication on `/admin/**` (and rename the URL prefix for consistency). For now, even basic-auth with a single bcrypted credential in `application.properties` is a meaningful step up.

### 5. No CSRF Protection — High

**Evidence:** No Spring Security present (see #4), and the JSON POST handlers in `GameRestController.java` accept `application/x-www-form-urlencoded` parameters (`request.getParameter("text")`) without verifying any anti-CSRF token. The session is identified solely by cookie.

**Impact:** A page on a different origin can trick a logged-in player's browser into POSTing to `/gameLogin.json`, `/gameCommands.json`, or `/gameMessage.json`. Concrete consequences:

- `/gameLogin.json` can register a fresh PlayerShip in a victim's session with an attacker-chosen name (used to defame, spoof, or create grief tools).
- `/gameCommands.json` can submit `STOP` (silently quitting the victim's ship) or arbitrary attack commands on the victim's behalf.
- `/gameMessage.json` can post chat to other players in the victim's name.

For a game this is mostly nuisance-grade, but it is still a textbook CSRF.

**Remediation:** With Spring Security, the default CSRF token filter handles this. Without Spring Security, at minimum require a custom header (e.g. `X-Requested-With`) that browsers will not send cross-site without an explicit preflight, and check `Origin`/`Referer` for state-changing endpoints. Set `SameSite=Lax` (or `Strict`) on the session cookie (see #7).

### 6. Session Fixation — High

**Evidence:** `src/main/java/org/ncombat/web/GameRestController.java:78–121` (`gameLogin`):

- Line 93–101: if a session already exists, it is reused.
- Line 113: `setCombatant(session, ship)` writes a `COMBATANT_ID` attribute into the existing session.
- The session ID is never rotated (e.g. via `request.changeSessionId()` or by invalidating the old session and creating a new one).

The only call to `session.invalidate()` is on player death (line 213).

**Impact:** Classic session fixation. Attacker visits `/gameJoin.json`, captures the `JSESSIONID` cookie the server hands out, plants that cookie in the victim's browser (e.g. via a sibling subdomain XSS, an open AP, or a coffee-shop network), then waits for the victim to log in. Once the victim has bound a `COMBATANT_ID` to that session, the attacker uses the pre-known JSESSIONID to drive the victim's ship.

**Remediation:** Rotate the session ID on every authentication boundary. In Servlet 3.1+, `request.changeSessionId()` is the right primitive. With Spring Security this is automatic (`sessionManagement().sessionFixation().migrateSession()`).

### 7. Insecure Cookie Attributes / No HTTPS — Medium

**Evidence:**
- `src/main/resources/application.properties` defines `server.port=5000` but does not set `server.servlet.session.cookie.secure`, `…http-only`, or `…same-site`.
- No `server.ssl.*` configuration; the app speaks plain HTTP.

**Impact:**
- Session cookie is **not** marked `HttpOnly` by default in older Spring Boot — JS (and therefore any XSS) can read `document.cookie`. (Spring Boot does default HttpOnly to `true` in recent versions, but the project explicitly relies on default behaviour with no test coverage for it; making it explicit is safer.)
- No `Secure` flag — cookie is sent over plaintext HTTP, observable on the wire.
- No `SameSite` — full CSRF surface (see #5).
- No HSTS, no `redirect` from HTTP to HTTPS.

**Remediation:**
```
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.secure=true
server.servlet.session.cookie.same-site=lax
```
Front the application with HTTPS (reverse proxy or `server.ssl.*`) and enable HSTS via Spring Security or the proxy.

### 8. Untrusted Text → DOM Without Explicit Sanitization — Medium

**Evidence:**
- `src/main/resources/static/html/lib/teletype.js:43-49` — `ttElem.innerHTML = ttElem.innerHTML + msg;` per character.
- `src/main/resources/templates/ncombat.html:39` / `ncombat2.html:39` — `$('#prompt').html(data.prompt);`
- Player-supplied text reaches `addMessage()` paths through `processMessageCommand` (`PlayerShip.java:432-449`) and through the "ship just appeared" / "ship just destroyed" formatted strings in `Combatant.java` and `GameServer.java`. Player names are merely uppercased and trimmed (`GameRestController.java:104`).

**Impact:** Today's exposure is limited by two coincidences:

1. The teletype writes one character at a time. Each write reads back `innerHTML` (which the browser serializes with entity-escapes for `<`, `&`, `"`), then re-parses. As a result, multi-character HTML tag fragments do not assemble across writes in modern browsers — they end up as text. *This is an implementation accident, not a defense.*
2. Prompts assigned via `.html()` are server-controlled constants (`"CMDS?"`, `"ENTER YOUR NAME?"`, etc.), so the `.html()` sink is currently fed only safe values.

If either condition is changed (e.g. the teletype is "fixed" to render whole lines for performance, the message channel ever emits a server-side admin notice that includes user input, or `.html()` is reused for a player-driven value), this immediately becomes stored XSS in a multiplayer chat channel.

**Remediation:**
- Render messages with `textContent` / `document.createTextNode`, never `innerHTML`.
- Replace `.html(data.prompt)` with `.text(data.prompt)`.
- Add a Content-Security-Policy header that forbids inline scripts and `unsafe-eval` (also addresses #3 indirectly).
- Server-side: escape or strip control characters and HTML-special characters from player names and chat messages before they enter the message list.

### 9. Log Injection via `requestedSessionId` — Medium

**Evidence:** `src/main/java/org/ncombat/web/GameRestController.java:357-373`:

```java
msg = "IP=" + request.getRemoteAddr()
            + ", requestedSession=" + request.getRequestedSessionId()
            + ", session=" + sessionId
            + ": INTERNAL ERROR: " + msg;
log.warn(msg);
```

`request.getRequestedSessionId()` returns the raw value of the client's `JSESSIONID` cookie (or `;jsessionid=` URL token). It is fully client-controlled and is **not** validated by the container before this point.

**Impact:** An attacker can supply a JSESSIONID like `legit\nWARN ncombat - Spoofed log line — IP=10.0.0.1` to forge log entries. This undermines forensic analysis, can bypass naive log-based alerting, and (if the logs feed a downstream consumer that interprets escape sequences, e.g. ANSI in a terminal viewer) can be used to obscure attacker activity.

**Remediation:** Strip CR/LF (and other control characters) from any user-controlled value before logging. A small helper or a logback `%replace` pattern suffices: `log.warn("IP={} requestedSession={} session={} msg={}", ip, sanitize(requestedSession), sessionId, msg);` with `sanitize` replacing `\r\n` and other control chars.

### 10. Unauthenticated Test Endpoint — Medium

**Evidence:** `src/main/java/org/ncombat/web/AppRestController.java:12` defines `/appTest.json` returning two static strings, with no auth.

**Impact:** Diagnostic endpoint left in production. Today it leaks only that the controller exists. Pattern is dangerous because such endpoints accrete behaviour over time.

**Remediation:** Delete it, move it behind admin auth (per #4), or guard it with a Spring profile (`@Profile("dev")`).

### 11. STOP-Command Validation Is a Silent No-Op — Low (logic / integrity)

**Evidence:** `src/main/java/org/ncombat/command/CommandParser.java:432`:

```java
public void validateStopCommand (StopCommand cmd) {
    if (combatant.nearestRange() < MIN_DISCONNECT_RANGE );
}
```

The stray semicolon makes the `if` body empty. The method does nothing.

**Impact:** Game-rule integrity, not classical security. A player can disconnect (`STOP`) while engaged in combat, bypassing the intended `MIN_DISCONNECT_RANGE` restriction — a way to dodge a `HNG`/kill credit by quitting cleanly when about to be destroyed. Players can exploit this to game the leaderboard / kill counts.

**Remediation:** Remove the trailing semicolon and decide on the intended behaviour — likely `throw new CommandValidationException("Cannot disconnect within " + MIN_DISCONNECT_RANGE + " km of another combatant.");`. Cover with a unit test in `CommandParserTest`.

### 12. Static Mutable Cache Initialised Under Instance Lock — Low (concurrency)

**Evidence:** `src/main/java/org/ncombat/command/CommandParser.java:35-85`:

- `parseMethods` and `validateMethods` are `static` fields.
- `loadMethodCache()` is `protected synchronized` — but `synchronized` on an instance method locks `this`, not the class. Two parsers built in parallel by two HTTP threads each hold their own lock and can race to initialise the static maps. Likewise, lazy reads from `parse()` happen without synchronization at all.

**Impact:** Today the race is benign — both threads will publish equivalent `HashMap`s — but `HashMap` is not safe for concurrent publication, and a partially-published map could be visible to a reader on another thread, causing a `NullPointerException` on a real command. Not a direct exploit, but a denial-of-service plausibly reachable by parallel logins on a cold JVM.

**Remediation:** Initialise the caches in a `static` initializer, or use a `synchronized` block on `CommandParser.class`, or switch to `ConcurrentHashMap` populated once via a static initializer. Removing the reflection-based dispatch entirely (a `switch` on the action character) is cleaner.

### 13. No Rate Limiting / DoS Protection — Low

**Evidence:** No filter, interceptor, or annotation in the source tree enforces per-IP or per-session request limits. The game cycle runs every 1 s (`GameServer.DEFAULT_CYCLE_PERIOD`) and the `playerSync()` monitor holds the HTTP thread for up to 5 s per command (`GameServer.PLAYER_SYNC_TIMEOUT`).

**Impact:** A modest number of attackers (~Tomcat default 200 worker threads / 5 s) can saturate the worker pool by spamming `/gameCommands.json`. Likewise `/gameLogin.json` can be flooded to fill all 15 ship slots, denying play to real users. `/gamePing.json` is a cheap unauthenticated GET that bumps `lastContactTime`, which can be used to keep zombie sessions alive.

**Remediation:** Add bucket4j or Spring's `RateLimiter`, or front with a reverse proxy that enforces per-IP rate limits. Cap the number of concurrent ships per source IP. Time out idle sessions (`server.servlet.session.timeout=15m`).

### 14. Google Analytics Loaded with `document.write` over Mixed Content — Low

**Evidence:** `templates/ncombat.html:111-120` and `templates/ncombat2.html:111-120`.

```js
var gaJsHost = (("https:" == document.location.protocol) ? "https://ssl." : "http://www.");
document.write(unescape("%3Cscript src='" + gaJsHost + "google-analytics.com/ga.js' …"));
```

**Impact:** Loads the legacy `ga.js` (deprecated) over HTTP when the page is served over HTTP. A network attacker can replace the response and execute arbitrary JS in the page context — same impact as #3. Even over HTTPS, the legacy tracker is unsupported and may be removed by Google.

**Remediation:** Remove the analytics block, or update to GA4 / a self-hosted analytics tool, loaded only over HTTPS, and remove `document.write`/`unescape` patterns.

### 15. Legacy `bin/` Module Retains Spring 5.2.20 and Other Old Deps — Informational

**Evidence:** `bin/pom.xml:21` pins `spring.version=5.2.20.RELEASE`; `bin/pom.xml:18-22` targets Java 1.7; `bin/pom.xml:16` pins `junit 4.13.1`; transitive deps not declared.

**Impact:** The module is not the active build (`pom.xml` at root supersedes it), but it is still part of the source tree, references the same `org.ncombat` group/artifact, and is the artifact Dependabot recently bumped (`f8b9adb`). If anyone publishes this WAR or includes it in CI, it will ship with an old Spring 5.2.x and a Java 7 baseline.

**Remediation:** Either delete `bin/` entirely (it appears to duplicate `docs/` and uses an older packaging), or convert it into a documentation-only artifact. If retained, update Spring to 5.3.x (the last supported 5.x line) and target a supported JDK.

### 16. Insecure `Math.random()` for Game RNG — Informational

**Evidence:** `GameServer.java:65-81`, `BotShip.java:177,277-278`.

**Impact:** Predictable randomness for ship positions, bot speeds, and trash-talk selection. For gameplay this is fine. The note is here purely so that any future use of this code for security purposes (session token generation, missile-spread cryptographic guarantees, etc.) does **not** copy this pattern. Use `java.security.SecureRandom` if randomness is ever used in a security-sensitive context.

## Hardening Checklist (Prioritised)

1. **Add `spring-boot-starter-security`** with a minimal `SecurityFilterChain`:
   - CSRF token on all state-changing endpoints.
   - HTTP Basic (or form login) requiring auth for `/admin/**`, `/appTest.json`, `/adminTest.json`.
   - `sessionFixation().migrateSession()`.
2. **Upgrade Spring Boot** to the latest 3.x (or 2.7.x with commercial support if you must stay on Java 8).
3. **Remove jQuery 1.3.2**; either upgrade to jQuery 3.7+ or replace with vanilla JS. Eliminate `eval()` and `$().html(<dynamic>)`.
4. **Set cookie attributes** in `application.properties`: `http-only=true`, `secure=true`, `same-site=lax`. Front with HTTPS.
5. **Sanitize message channels** server-side: escape or strip control chars and HTML-special chars from player names and chat messages before they enter `addMessage()`.
6. **Fix `validateStopCommand`** (CommandParser.java:432) — remove stray semicolon and surface the validation error.
7. **Sanitize log inputs** — strip CR/LF from `request.getRequestedSessionId()` before logging.
8. **Add a CSP header**: `default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none';` — confirm by exercising the app.
9. **Add OWASP Dependency-Check** to the build for ongoing CVE awareness.
10. **Delete or guard** `bin/`, `/appTest.json`, `/adminTest.json` — anything that exists "for testing".

## Methodology

- Static code review of all Java sources under `src/main/java`, all Thymeleaf templates and static assets under `src/main/resources`, and `pom.xml` / `bin/pom.xml`.
- Grep-based searches for security-relevant patterns: `eval`, `innerHTML`, `Math.random`, `Random`, `password|secret|token|api_key`, `Filter|Security|Csrf|PreAuthorize|Secured`, session cookie config, and reflective dispatch.
- Manual inspection of the request/response flow for each endpoint declared in the `web/` package and confirmation that **no Spring Security filter chain is registered anywhere in the source tree**.
- The legacy `bin/` module was checked at the manifest level only; it is not the active build target.

Dynamic testing (running the app, fuzzing endpoints, browser-based PoC) was **not** performed; findings are based on source analysis. Confirming the exploit sketches (especially #5 CSRF, #6 session fixation, and #9 log injection) with a running instance is recommended before patching.
